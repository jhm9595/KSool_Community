# 게임 개발자 전달용: 커뮤니티 진행도 연동 명세 v1

작성일: 2026-11-17 (KST)
커뮤니티 저장소: https://github.com/jhm9595/KSool_Community.git
상태: 커뮤니티 수신 로직 및 송신 참고 코드 작성·자동 테스트 완료. 운영 배포 및 실제 게임 연결은 미완료.

## 1. 요청 목적과 담당 범위

오른쪽 iframe 게임에서 플레이한 진행도를 왼쪽 커뮤니티의 숫자·해금 목록·사용 가능 재료에 반영합니다. 비로그인 사용자도 현재 브라우저에서 동작해야 합니다.

- 커뮤니티 담당: iframe 연결 요청, 메시지 검증·수신, 전체 스냅샷 반영, 모드 표시, 필터·숫자 계산, 클라우드 보조 조회.
- 게임 담당: 게임 초기화 완료 후 전체 진행도 생성, 상태 변경 시 송신, 5초 heartbeat, 운영 게임 배포.
- 기존 로그인·클라우드 저장 방식은 유지합니다. 새 DB나 인증 API는 필요하지 않습니다.
- 추천 투표 통합·랭킹 검증·기기 간 게스트 동기화는 범위 밖입니다.
- 본 저장소의 game-progress-bridge.js는 전달용 참고 파일이며 게임에 자동 설치되지 않습니다.

## 2. 화면 레이아웃

```text
┌──────────────────── 커뮤니티 상단 메뉴 ─────────────────────┐
│ 조합 / 커뮤니티 / 추천 / 랭킹 / 업데이트                    │
├────────────────────────────────────┬───────────────────────┤
│ 검색 · 새로고침 · 글쓰기            │ 오른쪽 게임 iframe    │
│ [✓ 게임 모드 따라가기]              │                       │
│ [퀴즈 12/84] [타이쿤 5/84]          │ 기존 게임 UI 유지     │
│ 게임창 연결됨 · 현재 플레이 기록    │                       │
│ 해금 진행률 / 사용 가능 재료        │ 별도 연동 버튼 불필요 │
│ 카테고리 · 전체/해금/미해금          │                       │
│ 조합 목록 또는 커뮤니티 게시판      │                       │
└────────────────────────────────────┴───────────────────────┘
```

84는 레이아웃 예시이며 실제 분모는 커뮤니티 도감 길이입니다. 모바일은 기존 게임 패널 열기/닫기 동작을 유지합니다. 패널을 접어도 iframe을 제거하지 않습니다.

기본은 게임 모드 따라가기입니다. 커뮤니티에서 퀴즈/타이쿤 버튼을 직접 누르면 따라가기를 끄며, 게임과 다른 모드를 보는 경우 안내합니다. 다시 체크하면 현재 게임 모드로 복귀합니다.

상태 문구는 연결 대기 / 게임창 연결됨 / 연결 끊김·마지막 기록 / 클라우드 저장 기록으로 구별합니다. 숫자 0만으로 연결 성공을 판단하지 않습니다.

## 3. 주소와 보안 경계

| 항목 | 운영 값 |
|---|---|
| 부모 커뮤니티 origin | https://ksool.minibig.pw |
| 자식 게임 origin | https://play.ksool.minibig.pw |
| 커뮤니티 iframe | index.html의 #game-frame |

postMessage의 targetOrigin에 위 정확한 origin을 사용합니다. '*'를 사용하지 않습니다. 경로와 마지막 슬래시는 origin에 포함하지 않습니다.

게임은 event.origin과 event.source === window.parent를 함께 검사합니다. 커뮤니티는 event.origin과 event.source === document.querySelector('#game-frame').contentWindow를 함께 검사합니다. localhost 시험 시 양쪽을 테스트 origin으로 명시적으로 바꾼 별도 설정이 필요합니다. 운영 허용 목록을 느슨하게 바꾸지 않습니다.

## 4. 연결 순서

1. 커뮤니티가 iframe load 시 새 requestId를 만들고 REQUEST를 보냅니다.
2. 초기화 중이라 받을 수 없으면 커뮤니티가 연결 대기 동안 5초마다 같은 REQUEST를 재전송합니다.
3. 게임은 신뢰할 수 있는 REQUEST의 requestId를 기억합니다. 새 requestId일 때 sequence를 0으로 초기화합니다. 같은 requestId 재요청에서는 초기화하지 않습니다.
4. 두 모드 초기화가 끝나면 전체 PROGRESS를 보냅니다. 초기화가 아직 끝나지 않았다면 기다립니다.
5. 커뮤니티는 검증 후 스냅샷을 적용하고 ACK를 보냅니다.
6. 게임은 변경 시 즉시, 변경이 없더라도 5초마다 전체 PROGRESS를 보냅니다.
7. 15초 동안 유효한 메시지를 받지 못하면 커뮤니티는 연결 끊김으로 표시하고 재요청합니다. 백그라운드 탭에서는 타이머 지연이 가능하며 복귀 후 재연결합니다.

ACK는 개발 확인용입니다. ACK가 없다고 게임 저장을 취소하거나 플레이를 막지 않습니다. heartbeat와 재요청으로 복구하며 별도 무한 재전송 큐는 만들지 않습니다.

### 부모 → 게임: 연결 요청

```js
{
  type: 'KSOOL_PROGRESS_REQUEST',
  version: 1,
  requestId: '부모가 생성한 UUID'
}
```

### 게임 → 부모: 전체 스냅샷

```js
{
  type: 'KSOOL_PROGRESS',
  version: 1,
  requestId: 'REQUEST에서 받은 값을 그대로 사용',
  sequence: 1,
  mode: 'quiz', // 'quiz' | 'tycoon'
  quiz: {
    unlockedRecipeIds: [1, 2],
    unlockedIngredientIds: [202, 206],
    purchasedIngredientIds: []
  },
  tycoon: {
    unlockedRecipeIds: [1],
    unlockedIngredientIds: [202, 206],
    purchasedIngredientIds: [301]
  }
}
```

- version은 정수 1입니다. mode는 소문자로 변환합니다.
- sequence는 requestId별 양의 안전한 정수이며 전송할 때마다 증가합니다. heartbeat도 증가합니다.
- 두 모드와 각 모드의 세 배열은 모두 필수입니다. ID는 양의 안전한 정수이며 각 배열은 최대 10,000개입니다.
- 초기화 완료 후 실제 기록이 없는 모드는 세 배열을 빈 배열로 보냅니다. 아직 읽지 못한 모드를 빈 배열로 보내면 안 됩니다.
- 전체 스냅샷으로 교체합니다. 증가분만 보내지 않습니다. 초기화로 ID가 줄거나 0개가 되어도 그대로 전달합니다.
- 이메일·토큰·닉네임·원본 세이브 전체·랭킹 점수는 전달하지 않습니다.
- 카운터를 따로 보내지 않습니다. 커뮤니티가 해금 ID를 중복 제거하고 자신의 도감 ID와 교차해 숫자와 필터를 함께 계산합니다.
- 게임에만 존재하는 새 레시피는 집계에서 제외되므로 출시 시 도감 데이터도 함께 갱신해야 합니다.
- 현재 HELP_FRIEND 등 보조 모드라면 직전에 선택한 quiz/tycoon을 유지합니다. 보조 모드를 별도 문자열로 전송하지 않습니다.

### 부모 → 게임: 수신 확인

```js
{
  type: 'KSOOL_PROGRESS_ACK',
  version: 1,
  requestId: '요청 ID',
  sequence: 1
}
```

알 수 없는 버전, 누락된 배열, 틀린 requestId, 이전 또는 중복 sequence는 무시하고 기존 기록을 유지합니다. 잘못된 메시지는 순서 번호를 소비하지 않습니다.

## 5. 게임 코드의 권장 위치와 적용 방법

현재 운영 JS를 읽어 확인한 이름을 기준으로 설명합니다. 실제 게임 저장소 버전에서 파일과 호출 위치를 확인해 적용해 주세요. 공개 KSool_Gemini 저장소에는 현재 리디렉션 HTML만 있어 이 문서 작성자가 게임을 직접 수정하지 않았습니다.

### 파일 배치

1. 본 저장소의 integration/game-progress-bridge.js를 게임의 src/js/services/CommunityProgressBridge.js로 복사합니다.
2. 게임 index.html에서 게임 app.js보다 먼저 defer script로 로드합니다.

```html
<script defer src="./src/js/services/CommunityProgressBridge.js?v=1"></script>
<script defer src="./src/js/app.js"></script>
```

이 순서에서 예제의 publish 함수를 아래 지점에서 호출합니다. 커뮤니티 프로젝트의 HTML에 게임용 bridge를 로드하는 방식이 아닙니다.

### 게임 상태 → 전달 데이터 변환

```js
// 의사 코드: 실제 게임의 인스턴스와 상태 필드에 맞춰 구현하세요.
function publishCommunityProgress() {
  if (!bothModesInitialized) return;
  window.KSoolCommunityBridge.publish({
    mode: currentMode === 'QUIZ' ? 'quiz' : 'tycoon',
    quiz: getCompleteQuizProgress(),
    tycoon: getCompleteTycoonProgress()
  });
}
```

getCompleteQuizProgress/getCompleteTycoonProgress는 예제 함수 이름이며 실제 API가 아닙니다. 세 필수 배열을 가진 객체를 반환하도록 작성합니다. 활성 모드는 메모리의 최신 inventory 값을, 비활성 모드는 해당 모드의 최신 저장 상태를 사용합니다. Set은 Array.from으로 변환합니다.

StorageService.exportUnifiedSyncPayload()가 두 모드 저장 상태를 반환하는 것은 확인했습니다. 다만 저장 전 메모리 변경이 있을 수 있으므로 이 메서드만 무조건 읽기보다는 상태가 저장·확정된 시점에 호출하거나 활성 모드 최신 상태를 반영해야 합니다. 저장 실패를 빈 진행도로 치환하지 않습니다.

### 호출 지점

| 지점 | 호출 시점 |
|---|---|
| 앱 초기화 | 두 모드 세이브 로드 및 기본 지급 적용 완료 후 |
| 조합 성공·레시피 해금 | inventory와 진행도 업데이트 완료 후 |
| 재료 해금·구매 | 해당 모드 상태 업데이트 완료 후 |
| selectGameMode | 모드 저장과 inventory 전환 완료 후 |
| CloudSyncService 병합·불러오기 | 병합 상태를 게임 메모리에도 적용한 후 |
| 세이브 가져오기·초기화 | 실제 현재 상태 교체 완료 후 |
| 게임 계정 변경 | 새 계정 상태 적용 완료 후 |

가장 좋은 위치는 여러 UI 버튼이 아니라 공통 상태 변경/저장 완료 지점입니다. 같은 작업에서 여러 번 변경된다면 짧게 묶어서 최종 상태를 한 번 publish해도 됩니다. bridge는 마지막 publish 스냅샷을 heartbeat로 다시 전송하므로 변경 시 publish를 빠뜨리면 기록도 갱신되지 않습니다.

로그인·DB 업로드 완료를 기다릴 필요는 없습니다. 게임 로컬 상태가 먼저 전달되고 클라우드 저장은 기존대로 진행합니다. 단독 게임 탭에서는 부모가 없으므로 전송하지 않습니다.

## 6. 기록 우선순위와 예외

- 최근 15초 이내 게임 메시지: 게임창 기록을 우선하며 클라우드는 덮어쓰지 않습니다.
- 연결이 끊겼거나 게임이 연결되지 않음: 커뮤니티 로그인 계정의 클라우드 저장 기록을 5초 주기로 확인합니다.
- 로그인 없음/조회 실패: 마지막 기록을 유지하며 출처 또는 오류를 표시합니다.
- 게임 메시지 수신 전에 시작한 클라우드 응답은 늦게 도착해도 무시합니다.
- 게임창 계정과 커뮤니티 계정이 다를 때도 연결 중에는 게임창을 표시합니다. 이 기록을 커뮤니티 계정의 클라우드에 업로드하지 않습니다.
- 커뮤니티의 기록 초기화는 게임 초기화 명령이 아닙니다. 게임이 연결되어 있으면 다음 스냅샷으로 다시 표시될 수 있습니다.
- 메시지 수신 기록은 화면 표시용입니다. 보상·결제·랭킹 신뢰 근거로 쓰지 않습니다.

## 7. 양쪽 검증 체크리스트

| 시나리오 | 기대 결과 |
|---|---|
| 비로그인 게임 시작 | 초기 전체 기록 수신, 연결 상태 표시 |
| 퀴즈 조합 1개 해금 | 다음 변경 메시지에서 숫자와 해금 목록이 함께 변경 |
| 타이쿤 전환 | 따라가기 ON이면 사이트 모드도 전환 |
| 따라가기 OFF 후 게임 전환 | 사이트 선택 유지, 모드 차이 안내 |
| 게임 초기화 | 해당 모드 빈 배열로 교체, 예전 해금이 남지 않음 |
| 재료 구매 | 추천에서 사용 가능한 재료 판단 변경 |
| 게임 iframe 새로고침 | 새 requestId로 재연결 |
| 계정 변경·가져오기 | 교체 완료 후 최신 전체 상태 반영 |
| 게임 패널 접기·다시 열기 | 게임 상태 유지, 연결 복구 |
| 15초 넘는 메시지 중단 | 연결 끊김 안내, 마지막 기록 또는 클라우드 보조 표시 |
| 잘못된 출처·창·버전·순서·부분 payload | 기존 기록 유지 |
| 클라우드 응답 지연 | 더 최근 게임 메시지를 덮어쓰지 않음 |
| 게임 단독 탭 | 기존 플레이 정상, 부모 통신 오류 없음 |

브라우저 개발 도구에서 REQUEST → PROGRESS → ACK가 이어지는지 확인하세요. 기대 반영 시간은 게임의 상태 변경 publish 이후 정상적인 전경 탭에서 1초 이내를 목표로 하되, 네트워크가 아닌 브라우저 메시지 처리·렌더링 기준입니다.

자동 테스트는 npm test로 실행합니다. 수신기·송신 참고 코드의 모의 연동은 검증했으나 실제 운영 게임, Google 로그인, 모바일 WebView의 종단 간 검증은 양쪽 배포 후 필요합니다.

## 8. 커뮤니티 구현 파일

- progress-protocol.js: payload 형식·버전·requestId·sequence 검증
- app.js: origin/source 검사, 요청·ACK, 스냅샷 교체, 클라우드 충돌 방지, 상태·모드 UI
- index.html 및 scripts/build.mjs: 수신기 로드 및 배포 산출물 포함
- integration/game-progress-bridge.js: 게임 개발자용 송신 예제 (운영 게임에 별도 설치 필요)
- tests/progress-protocol.test.mjs: 핸드셰이크·heartbeat·초기화·잘못된 메시지 테스트

게임 개발자가 전달할 완료 정보: 적용한 파일/커밋, 게임 배포 주소, 실제 publish 호출 지점, 위 체크리스트 결과. 양쪽을 같은 규격으로 배포해야 연결됩니다.
